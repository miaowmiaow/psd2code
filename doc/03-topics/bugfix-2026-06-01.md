## 1. 渐变叠加（GradientOverlay）渲染参数缺失

**文件**: `scripts/core/render/effects/overlay_renderer.py`

**问题描述**:
原有的渐变叠加渲染器未解析 PSD 中的多个关键参数，导致渐变效果与 Photoshop 实际表现不一致：

- **缩放比例 (`Scl `)**: PS 中渐变可设置 Scale（默认 100%），之前未读取该值，导致渐变跨度始终为默认范围。
- **与图层对齐 (`Algn`)**: "Align with Layer" 标志未解析。当启用时，PS 的渐变范围基于图层尺寸而非对角线长度；未对齐时使用对角线。之前一律使用固定的 `max_proj` 计算方式，导致窄长图层（如 18×1864）上的近水平渐变或宽扁图层上的垂直渐变表现严重偏差。
- **偏移 (`Ofst`)**: 渐变中心偏移百分比未解析，导致有偏移的渐变渲染位置错误。

**修复方案**:
1. 解析 `Scl `、`Algn`、`Ofst` 三个参数；
2. 线性渐变：
   - `align_with_layer=True` 时，`max_proj = (h / 2.0) * grad_scale`（基于图层高度 × 缩放）；
   - `align_with_layer=False` 时，`max_proj = half_diag * grad_scale`（基于对角线 × 缩放）；
3. 径向渐变：类似地区分 align 模式，使用半对角线或中心距离作为最大半径；
4. 中心点坐标加入偏移修正：`cx += offset_x_pct * w`，`cy += offset_y_pct * h`。

## 2. 含叠加效果的组未走 Hybrid 渲染路径

**文件**: `scripts/core/extract/layer_exporter.py`

**问题描述**:
psd-tools 的 `composite()` 对 GradientOverlay / ColorOverlay 渲染存在 Bug（尤其是 "Align with Layer" 时使用错误的渐变范围），导致直接使用 composite 合成出的图片渐变效果不正确。

之前的逻辑仅在检测到**效果溢出**（如投影、外发光等需要扩展 bbox 的效果）时才走 hybrid 路径。但渐变叠加/颜色叠加属于"非溢出型"效果（不会超出图层边界），不会触发 `expand > 0` 条件，因此这些组仍走了 psd-tools 的 composite 路径，输出结果有误。

**修复方案**:
1. 新增 `_group_has_overlay_effects()` 方法，递归检测组内是否有激活的 GradientOverlay / ColorOverlay 效果；
2. 在组渲染入口将判断条件从 `expand > 0` 扩展为 `expand > 0 or has_overlay_effects`；
3. 当仅因 overlay 效果触发 hybrid（`expand == 0`）时，**不再**用 psd-tools 的 composite 覆盖内部区域（因为 composite 对渐变叠加渲染有误），完全依赖我们自己的 hybrid 渲染结果。

## 3. 光效穿透（Light Blend Penetrate）组级排除逻辑不完整

**文件**: `scripts/core/extract/layer_exporter.py`

**问题描述**:
光效穿透机制会将 COLOR_DODGE / SCREEN 等恒等色混合模式的光效叶层标记到 `_suppressed_light_layers` 中，在后续 cluster 合成时排除这些层（因为它们在黑色/透明背景上 composite 会暴露为真实黑底）。

但存在一种情况：cluster 的成员可能是一个 PASS_THROUGH 组，该组内**所有可见子层**都是已被抑制的光效层。由于 `_suppressed_light_layers` 只记录叶层的 `id()`，不会直接匹配父组，导致这个"全光效子层"的组未被排除，composite 时产生黑色污染。

另外，当 cluster 的所有成员都被排除后，原代码仍会尝试 composite，浪费资源且可能产生异常。

**修复方案**:
1. 新增 `_is_fully_suppressed_group()` 方法，递归判断：若一个 PASS_THROUGH 组的所有可见子层要么已在 `_suppressed_light_layers` 中，要么本身是恒等色混合模式的光效层，则该组整体视为"已抑制"；
2. 在 `_merge_cluster_layers_as_image()` 中对每个 cluster 成员额外调用 `_is_fully_suppressed_group()` 检查；
3. 新增早退逻辑：当所有成员都被排除时直接返回 `None`，跳过无效合成。

## 4. 光效穿透合成目标选择优化（无效白色目标过滤）

**文件**: `scripts/core/extract/layer_exporter.py`

**问题描述**:
光效穿透 Phase 3 在向外查找目标图层时，只检查 bbox 交集 + 不透明像素存在性，不检查目标颜色值。当目标层是纯白/高亮度（如"背景"层），光效合成在数学上无效（`COLOR_DODGE(white, fg) = white`），但光效层仍被正常抑制导出。

在 `web.psd` 中，`组40`/`组40拷贝` 的 COLOR_DODGE 光效层向外穿透时同时匹配到白色"背景"和有效暗色目标。虽然光效确实被合成到了有效目标（cluster0/1 等），但这些有效目标的覆盖面积不及光效层全区域，导致部分光效视觉丢失（尤其是覆盖范围超出 cluster 区域的光晕边缘）。

**修复方案**:
1. Phase 3 新增 `_is_effective_light_target()` 方法：检查目标层交集区域内不透明像素的平均亮度，亮度 >= 0.92 时跳过（光效合成到此目标无意义的视觉变化）；
2. Phase 5 新增"降级 CSS blend"路径：当光效层的所有穿透目标都被亮度过滤（penetrate_map 中无记录）时，标记为 `fallback_css_blend`，不加入抑制集合；
3. 降级光效层在 `_export_layer_image` 中走 `_remove_identity_color()` 去除恒等色黑底（用亮度衰减 alpha），然后正常导出 + CSS `mix-blend-mode`；
4. 降级光效层在 cluster composite 中同样被排除（避免黑底）；
5. `_is_fully_suppressed_group()` 同步识别降级光效层。

## 5. PNG 透明边裁剪（trim）后 CSS url 引用不同步

**文件**: `scripts/targets/html/pipeline.py`

**问题描述**:
`PrunePreOptimizeStage` 中的 `_trim_transparent_borders` 操作会裁剪 PNG 透明边并生成新文件名（如 `img-233e8b-trim-c69ed7.png`），同时在内存中的 `css_rules` 字典中更新 url 引用。但写回 `style.css` 的条件仅检查 `pruned_n > 0`（被遮挡层剔除数量），不检查 trim 数量。

当只有 trim 操作生效（`trimmed_n > 0`）而没有遮挡层被剔除（`pruned_n == 0`）时，修改后的 CSS（含新 url）不会被写回文件。原 PNG 被删除（引用归 0），而 CSS 仍引用旧文件名 → 图片加载 404。

**修复方案**:
将写回条件从 `if pruned_n > 0` 扩展为 `if pruned_n > 0 or trimmed_n > 0`，确保 trim 修改也触发 CSS 写回。

## 6. CSS 类名以数字开头导致选择器无效

**文件**: `scripts/common/semantic.py`

**问题描述**:
PSD 图层名 `"18th Anniversary"` 经 `extract_semantic_token()` → `_to_kebab()` 归一化后得到 `"18th-anniversary"`，拼接后 CSS 选择器为 `.18th-anniversary__46`。

根据 CSS 标识符规范，类名选择器不能以数字开头（`[0-9]` 不在 `nmstart` 字符集中）。浏览器会**完全忽略**该选择器对应的整条规则——元素没有 width/height/background-image 等样式，视觉上"消失"。

**修复方案**:
在 `_to_kebab()` 函数末尾增加检查：如果归一化结果以数字开头，自动添加 `"n"` 前缀（`"18th-anniversary"` → `"n18th-anniversary"`）。这样 CSS 选择器 `.n18th-anniversary__46` 合法，浏览器正确解析。

## 7. Hybrid 渲染中调整层 Clip + Overlay Effects 冲突导致渐变叠加丢失

**文件**: `scripts/core/extract/layer_exporter.py`

**问题描述**:
`_render_group_with_hybrid_strategy` 中处理 clipping 层时，当 clip 层包含调整层（如"曲线 8"、"色相/饱和度"等 `kind` 不是 pixel/shape/smartobject/type/group 的层），会走 `has_adjustment_clip=True` 分支，使用 `group_layer.composite(viewport=base_bbox)` 渲染整个 base + clip 组合。

但 psd-tools 的 `composite()` 对 GradientOverlay / ColorOverlay 渲染有已知 Bug（这也是为何组整体走 hybrid 路径的原因）。当 base 层同时有渐变叠加效果时，composite 的输出会丢失渐变——整个组变为近乎均匀的颜色。

**典型案例**:
`组 36/框/组 1 拷贝` 内部结构：
- `矩形 4` (shape, base) — 有 GradientOverlay (angle=-90°, 6 色标)
- `图层 16` (pixel, clipping=1) — 纯像素层
- `曲线 8` (curves, clipping=1) — 调整层

因为 `曲线 8` 是调整层，走了 `has_adjustment_clip` 分支 → `composite()` 丢失 `矩形 4` 的渐变叠加效果。

**修复方案**:
1. 新增 `base_has_overlay` 检测：在进入 `has_adjustment_clip` 分支前检查 base 是否有活跃的 GradientOverlay / ColorOverlay 效果；
2. 当 `has_adjustment_clip=True` 且 `base_has_overlay=True` 时，不走 composite 分支，改为：
   - 用 `render_layer_with_effects` 渲染 base（保留渐变叠加效果）
   - 手动合成纯像素 clip 层
   - 对于调整层的影响，通过 **ratio-transfer** 算法提取：分别获取"仅 base"和"base + 调整层"的 composite 结果，计算颜色比值 `ratio = adj_result / base_result`，将比值应用到已渲染渐变的结果上
3. 最终用 base 原始 alpha 裁剪并合成到 canvas

**验证结果**:
- 修复前 `img-13f9b0.png` 纵向颜色方差：R=0.2, G=0.3, B=0.7（几乎无渐变）
- 修复后 `img-c2f475.png` 纵向颜色方差：R=74.8, G=63.1, B=70.3（渐变恢复）
- 与 `render_layer_with_effects` 参考结果像素级接近（差异 < 3）
