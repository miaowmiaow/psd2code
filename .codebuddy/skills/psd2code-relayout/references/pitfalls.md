# 重建过程中的实测坑位

按「会让你白跑一轮」的程度排序。每条都在南瓜大作战的道具墙上复现过。

## 1. 列间距不等时，不能写 `column-gap`

实测列起点：`47 / 222 / 398 / 573`，列宽 `142 / 142 / 142 / 139`。

```
gap1 = 222 - (47+142) = 33
gap2 = 398 - (222+142) = 34   ← 不是 33
gap3 = 573 - (398+142) = 33
```

用 `column-gap: 33px` 之后：

```
col3 实际 397（应为 398）
col4 实际 572（应为 573）
```

差 1px，视觉上看着"差不多"，但整列轮廓全部错位，区域差异 **23.8%**。

**正确做法**：把间隙并进轨道宽——

```css
grid-template-columns: 175px 176px 175px 139px;  /* = 本列宽 + 到下一列的间距 */
```

行同理（行距 207/207/207/206），用 `grid-template-rows` 逐行给值。

## 2. 矮格不是顶对齐，要补 `margin-top`

宝箱列 139×185，标准格 142×196。同一行的 `top` 相差 13px（宝箱格在行内下移）。

grid 默认 `align-items: stretch`，会把矮格拉到行高；改成 `start` 后仍是从行顶开始，于是整列上移 13px → 该列差异 **87,497 像素**。

**正确做法**：每格记录 `dy = 格.top - 行.top`，写成 `style="margin-top:{dy}px"`。

## 3. 坐标必须浏览器实测，不能用 CSS 累加

原产物的层级是 `#canvas ▸ rounded ▸ section-bg-3 ▸ prop ▸ prop-icon`，每层的 `left/top` 都是相对**各自父级**的。静态累加有两个致命问题：

- flex 容器内的子元素用 `margin` 定位，根本没有 `left/top`；
- 相对定位链里只要有一层算错，整块偏移。

实测：静态累加算出的坐标，第一次跑区域差异 **61.7%**。

**正确做法**：`getBoundingClientRect()` + `scrollX/scrollY`，一次拿准。

## 4. 新节点挂到父容器下，坐标要转相对

`.prop-wall` 的 `left/top` 如果直接写页面绝对坐标 `47 / 678`，而它被 append 到 `rounded`（页面坐标 `19 / 470`）下，实际位置就成了 `66 / 1148`——整块跑到屏幕外。

**正确做法**：`left = 47 - 19 = 28`，`top = 678 - 470 = 208`。

## 5. 文字用 `visibility: hidden`，不要用 `display: none`

截图前要拿到"纯图形"。用 `display: none` 会让文字脱离文档流，行高、容器高度都可能变，截出来的图形就和真实渲染不一致。

`visibility: hidden` 保留占位，只隐藏绘制 → 几何不变。

## 6. 替换 DOM 后必须清死规则

被替换掉的子层（`prop` / `prop-icon` / `rounded-24` …）在 DOM 里已经不存在，但它们的 CSS 规则还在。

不清理的话：`div` 减了 191，CSS 规则只减 5 条，文件体积反而可能变大。

**做法**：重建后收集 DOM 里所有仍被引用的 class，删掉其余 `^\\.class { … }$` 规则。产物是静态的，不存在运行时加 class 的情况。

实测：规则从 464 → 272（删掉 196 条）。

## 7. 不要期待零像素差

图形是渲染截图，理论上零误差；但文字是重新用 DOM 渲染的，字形抗锯齿、亚像素定位必然有差。

实测残差 0.41%，`max_delta = 190`（个别字形边缘），肉眼不可见。

**判定要看差异分布**：集中在文字行 = 正常；集中在图形轮廓 = 位置算错，回去查 `track_w` / `dy`。

## 8. 截图 clip 要用 `full_page=True`

页面高度 6778px，远超视口。`page.screenshot(clip=..., full_page=True)` 时 clip 用**页面坐标**；不加 `full_page` 且 clip 超出视口会直接报错
`Clipped area is either empty or outside the resulting image`。

## 9. 图层合成要按 DOM 文档顺序，不是 z-index

`z-index` 只在**同一层级**内比较；父子之间永远是「父先画、子后画」，与 z 值无关。

实测（宝箱列）：

| 图层 | box | z | 关系 |
|---|---|---|---|
| `prop-bg-18` | `[-5, 96, 140, 80]` | 103 | 底板 |
| `btn-locked` | `[26, 120, 77, 31]` | 101 | **它的子元素** |

按 z 排序会先画 `btn-locked`、再画底板 → 「待开启/领取」文字被底板盖住，整列差异 6,438 像素。

改成按 `querySelectorAll` 的文档顺序（先序）叠放，差异降到 300 像素。

## 10. 图层可能负坐标或超出列盒，画布要扩再裁

宝箱列的底板是 `[-5, 96, 140, 80]`（左溢出 5px、右溢出 1px），图标是 `[5, -5, 122, 108]`（上溢出 5px）。

直接按列尺寸建画布，`alpha_composite` 遇到负坐标会错位/丢内容。

**正确做法**：

```python
min_x = min([0] + [l['x'] for l in layers]);  max_x = max([w] + [l['x']+l['w'] for l in layers])
canvas = Image.new('RGBA', (max_x-min_x, max_y-min_y), (0,0,0,0))
...   # 合成时坐标减去 min_x / min_y
canvas = canvas.crop((-min_x, -min_y, -min_x+w, -min_y+h))   # 最后裁回列尺寸
```

## 11. 不要把整格截成不透明 PNG

用 `page.screenshot(clip=格box)` 得到的是**含父容器底色**的不透明图。后果：

- 背景被固化进图片，换肤/改底色就接不上；
- 20 个格子存 20 份完整截图（450 KB），而实际只有 5 种；
- 素材失去复用性（原产物里「南瓜」是一张复用的 `img-d83eb4.png`）。

**正确做法**：逐层取原始 PNG + 透明画布合成，再按内容 hash 去重。实测同样 20 格：

| 方案 | 张数 | 总大小 | 透明 |
|---|---:|---:|---|
| 整格截图 | 20 | 450 KB | 否 |
| 逐层合成 + 去重 | **5** | **119 KB** | 是 |

## 12. 背景板比容器大时，底部一定被裁

背景图是**固定尺寸**的，它不会撑开容器，绘制范围又被限制在容器的 `padding box` 内。所以只要「背景高 + 偏移 > 容器高」，超出部分直接消失。

实测（南瓜页）：

| 元素 | 范围 | 结果 |
|---|---|---|
| `.rewards` 容器 | 1900 ~ 3974 | — |
| 橙色板 `img-0856c7` | 2304 ~ 4006 | 超出 32px **被裁** |
| `.rewards__actions`（三按钮） | 3896 ~ 3974 | 底边正好压在裁切线上，看上去"被切掉" |
| `.comments__board` | 4052 ~ 5394 | — |
| 白卡底 `rounded-29d45d` | 4162 ~ 5408 | 超出 14px **被裁** |
| `.comment-input` | 5324 ~ 5394 | 同上，底部被切 |

**判定方法**（改之前先算一遍，不要等看截图）：

```
容器高 ≥ 背景 offset + 背景高
```

不成立就补 `padding-bottom`，让容器至少包住背景的可见部分。

## 13. 负 margin 上移容器会改变绘制顺序

标题被橙色板盖住，原因不是 z-index，是**绘制顺序**：

```
.comments__head   (4045~4150)   DOM 在前
.comments__title  (4038~4143)   margin-top: -7px
.comments__board  (4052~5394)   margin-top: -98px, DOM 在后
```

`board` 用负 margin 上移到 4052，正好落进标题的区间；它又排在 DOM 后面，于是整块不透明背景盖住了标题下半部分。

负 margin 是"移动"，不是"层叠"。**移动后如果和前面的兄弟元素重叠，重叠区的可见性由 DOM 顺序决定**——想让它显示在下面，就必须把 DOM 放到后面；想显示在上面，DOM 要放前面，或者给重叠部分留出空间（padding）。

判定信号：一个带背景的元素用了负 `margin-top`，且它前面的兄弟元素是**文字或图标**——大概率会盖住。

## 14. 合图必须用「缺失即失败」的写法，并在合成后验证输出

**同一个错误犯过两次**，都是文件名记错、文件不存在、静默跳过、只合到底图：

| 按钮 | 我写的文件名 | 实际文件名 | 结果 |
|---|---|---|---|
| 去回帖 | `quhuitie-3f2a4c.png` | `quhuitie-3f07af.png` | 纯蓝底无字 |
| 待助力 | `daizhuli-8b2e91.png` | `daizhuli-a33b2c.png` | 纯蓝底无字 |

根因只有一条：`compose()` 里写了 `if not f.exists(): continue`。

### 必须使用的写法（不要改）

```python
def compose(images_dir: Path, names: set[str], x0, y0, x1, y1, out: str):
    """合成多层叠图。素材缺失立即失败——绝不静默跳过。"""
    # 1) 先验文件，缺一个就停
    missing = [n for n in sorted(names) if not (images_dir / n).exists()]
    if missing:
        raise SystemExit(f"素材缺失，检查文件名：{missing}")

    sel = [i for i in assets if i['src'] in names
           and x0 <= i['bbox'][0] < x1 and y0 <= i['bbox'][1] < y1]
    # 2) 再验「命中的层数」，少一层也是错
    if len({i['src'] for i in sel}) != len(names):
        got = {i['src'] for i in sel}
        raise SystemExit(f"图层未命中：缺 {sorted(names - got)}")

    ...  # 合成
```

两个检查缺一不可：

- **文件存在**：挡住文件名写错；
- **图层命中**：挡住坐标范围写错（文件在、但不在这个 bbox 里）。

### 合成后必须验证输出

尺寸正确 ≠ 合成正确。文字类合成图要检查「文字层到底有没有进去」：

```python
im = Image.open(images_dir / out).convert('RGBA')
px = im.load()
white = sum(1 for y in range(im.height) for x in range(im.width)
            if px[x, y][:3] == (255, 255, 255) and px[x, y][3] > 200)
print(out, im.size, '白字像素=', white)   # 纯底图 ≈ 0~30；有文字 ≈ 300+
```

实测：`ui-btn-pending` 空图 32 个白像素，修好后 531 个。

注意这个指标只适用于**白字按钮**。黑字带白描边的按钮（如 `ui-3btn-*`）白像素只有 20~50，`ui-3btn-1` 是 22 但文字完好——**不要用统一阈值判定，要放大看一眼**。

### 为什么像素对比抓不到

- 一个空按钮的颜色和原版几乎一致，整页差异只多 0.02%；
- `verify_page.py` 只会说"这里不一样"，不会说"文案没了"；
- 视觉对比时，蓝色按钮有没有白字，在缩略图里看不出来。

**这类错误只能靠合成阶段的断言拦住。**

## 15. 写格子结构前先数资源层数，不要凭"看起来该有几个元素"

南瓜页「已领取」宝箱格，我手写成 3 个元素（宝箱 / 灰条 / 白字按钮），实际原版有 **6 层**：

| 原版图层 | 尺寸/位置 | 我画了 |
|---|---|---|
| `img-ecff76` 宝箱 | 117×113 @890 | ✅ |
| `rounded-3a0f0d` 深色圆底 ×2 | 58×58 @909 | ❌ |
| `img-b3731b` 印章图标 ×2 | 48×48 @914 | ❌ |
| `img-658bbe` 闪光 | 63×67 @916 | ❌ |
| `rounded-d68174` 「去拿糖果」竖条 | 50×165 @955 | ❌ |
| `rounded-d8ec77` 灰底 | 140×80 @994 | ✅ |
| `btn-received` 白字 | 69×22 @1023 | ✅ |

后果：缺失的深色圆底 + 印章原本压在按钮上沿，是按钮的视觉分界。少了它们，**浅灰底 + 纯白字**直接暴露在深紫背景上，成了一块看不清的白斑。

### 别把"对比度低"当成原因

| 因素 | 性质 |
|---|---|
| 文字纯白 (255) + 底浅灰 (227) | **既有设计**，原版一模一样，不是错误 |
| 缺 4 层深色元素 | **根因** |
| 对比度低 | **放大器**——它只是让"缺层"的后果更容易被看见 |

把对比度当成根因，会去改颜色（而原版本来就是这个颜色），真正的问题（少画了层）反而被掩盖。

### 做法

写任何一格/一张卡之前，先从 `assets.json` 把该 bbox 内的资源全部列出来，逐条标注它在结构里的角色：

```
bbox(568, 890, 140, 200) →
  img-ecff76      宝箱主体
  rounded-3a0f0d  已领取印章底（×2）
  img-b3731b      印章图标（×2）
  img-658bbe      闪光装饰
  rounded-d68174  竖排按钮（decor，脱离流）
  rounded-d8ec77  按钮底条
  btn-received    按钮文字
```

数量对不上就是漏了。**像素对比只能报"这里不一样"，报不出"少了哪几层"。**

## 16. 硬编码的 margin 不能跨用在不同尺寸的同构单元上

三张任务卡的标题结构相同（底条 + 文字），我写了一个规则：

```css
.task-card__title-text { margin-left: -135px; }
```

`-135` 是按第一张卡算的（底条 135 宽、文字 126 宽）。但第三张卡的底条是 **227** 宽、文字 217 宽，这个值完全不适用：

| 卡片 | 底条宽 | 文字理想 x | 实际 x（用 -135） |
|---|---:|---:|---:|
| 每日任务 | 135 | 5 | 5 ✓ |
| 每周任务 | 135 | 5 | 5 ✓ |
| 好友助力 | **227** | 5 | **92** ✗ |

后果：第三张卡的标题文字被推到 x=92，压在底条右半边。

**根因**：把「相对自身尺寸的偏移」（文字比底条左移 5px）表达成了「相对某个具体宽度的绝对值」（-135）。

正确写法：**让底条成为背景，文字是唯一子元素**，偏移相对自身：

```html
<div class="task-card__title" style="background:url(images/rect-9a4a7b.png) no-repeat 0 12px">
  <img class="task-card__title-text" src="images/friend-3c1e96.png" alt="">
</div>
```

```css
.task-card__title { display: flex; height: 47px; }
.task-card__title-text { margin-left: 5px; }   /* 相对底条左缘 5px，与宽度无关 */
```

这样三个宽度不同的标题用同一条规则，全部正确。

**判定信号**：一个 `margin` 的值来自「某个元素的宽度 − 另一个元素的宽度」。凡是这种算法得出的值，都不能跨用。

## 17. 合成图不要框进装饰层，只框槽位本身

评论区标题合成后是 **209×105**，但原版的标题本体只有 **135×72**（`comment-dbed57`），多出来的部分是装饰 `shape-25cf26`（209×101）。

后果：合成图位置对齐了（x=46），但因为高了 33px，它和下方橙色板的重叠区从原版的 65px 变成 91px —— 视觉上「黄板压上来太多」。

| | 尺寸 | 范围 | 与 board(4052) 重叠 |
|---|---|---|---|
| 原版标题 | 135×72 | 4045~4117 | 65px |
| 我的合成图 | 209×105 | 4038~4143 | **91px** |

**规则**：合成只发生在「一个槽位内」——槽位是标题本体，就把装饰排除在外。

- 装饰层如果**在槽位后面**（z 更低）→ 单独放，不合成；
- 装饰层如果**和槽位同层、必须一起**（如南瓜的宝石）→ 才合成。

判定：装饰层超出槽位本体范围（这里是宽的 209 vs 135、高 101 vs 72），说明它是"背景装饰"而非"本体的一部分"。

## 18. 改文件必须断言，改完要「读回」验证

### 症状：改了四轮，页面纹丝不动

评论区卡片底栏一直落在卡内（相对卡片 y=468，目标 496）。我连续改了四次：

1. `position: absolute; top: 496px`
2. 改成固定高度 + margin
3. 又改回 absolute
4. 再调 margin

每次"改完"都重算，结果一直是 468。

**真相**：CSS 里那条规则一直是 `margin: 20px 0 0 8px`，我写的四次替换**一次都没生效**。

```python
t = t.replace("""  margin: 60px 0 0 -78px;""", """  position: absolute; ...""")
# CSS 实际是 margin: 20px 0 0 8px → 找不到 → 什么都不做 → 不报错
```

`str.replace()` 匹配不到就静默返回原串。我以为改了，实际没改，然后在**错误的状态上反复调参数**——四轮全废。

检查 computed style 才发现：`footPos: 'static'`、`footMargin: '20px 0 0 8px'`——和我"写的"完全对不上。

### 必须这样改

```python
old = """.comment-card__foot {
  display: flex;
  margin: 20px 0 0 8px;
  width: 611px;
}"""
assert old in t, f"待替换文本不存在，实际内容已变：{old[:60]}"
t = t.replace(old, new)
```

**`assert old in t` 是硬要求**。它挡住的不只是"文本写错"，还有"上一轮已经改过、现在文本又变了"。

更稳的做法（多行规则用）：

```python
import re
pat = re.compile(r'\.comment-card__foot\s*\{[^}]*\}')
assert pat.search(t), '规则不存在'
t = pat.sub(new_rule, t)
```

### 改完必须读回 computed style

编辑器里的 CSS 写对了，不等于浏览器里生效——可能被后面的同名规则覆盖、被继承值影响、或被 `!important` 压掉。

```js
getComputedStyle(el).position   // 应为 'absolute'，如果是 'static' 说明没生效
getComputedStyle(el).top        // 应为 '496px'，如果是 'auto' 说明没设上
```

实测就是这样发现问题的：`footPos: 'static'`。

**判定顺序**：

| 检查 | 说明 |
|---|---|
| 改完立刻 `grep` 该规则 | 确认文件里真的是新内容 |
| 再读 computed style | 确认浏览器里真的生效 |
| 最后才看像素/截图 | 前两步都没问题，才有资格谈"效果" |

我之前直接跳到第三步——看到位置没变就调参数，从没怀疑"改没改上"。**这四轮的时间全浪费在这里。**

## 19. 文字形态看 DOM，不看眼睛

产物里那段「完成任务获得糖果…全部点亮后可获得【盛典狂欢捣蛋箱】」的说明文字，我看到是白字 + 橙色高亮，就认定它是文本层，手打了一段 `<p>` 并自己加了 `<span class="hl">`。

实际它是一张图：`task-abd00c.png`（619×103）。

```json
// assets.json
"txts": []        // 0 个文本 —— 该产物所有文字都已转成图片
```

### 判断方法（唯一可靠）

```python
d = json.loads(Path('assets.json').read_text())
has_text = len(d['txts']) > 0
# True  → 有文本层，按 <span> 取原文
# False → 全部是图，每个"文字"都该在 d['imgs'] 里找到对应 png
```

不要靠这三样判断：看着像文字、颜色像文字、位置像文字。**图的渲染和文本渲染在截图上是无法区分的。**

### 手打文本的代价

| | 手打 | 用原图 |
|---|---|---|
| 字体 | 系统字体 | PSD 原字体 |
| 字距 | 浏览器默认 | 设计稿字距 |
| 高亮色 | 我猜的 `#ff8c1a` | 原图自带 |
| 折行位置 | 我加的 `<br>` | 原图固定 |
| 还原度 | 该区域 20% 差异 | 逐像素一致 |

实测：改回图片后 `position` 占比不变（仍是 1.1%），但那块差异从 20% 降到接近 0——**用原图永远比手打准确**。

### 规则里的坑

原规则写的是「文本 → 取 `<span>` 原始文本，保持 DOM 文本」＋自检项「文字全部是 DOM 文本」。

在「产物文本已转图」的稿子上，这条会**主动把人推向手打文本**：找不到 span，就自己编一段。

已改成：

> 文字还是图片，由 DOM 的真实属性决定，不能凭视觉判断。
> `txts` 为 0 → 当作图片引用，禁止手打。

## 20. 猜数值是返工的根源：骨架看截图，数值查 CSS

### 实测代价

南瓜整页手写，从 74% 爬到 77%，用了 **20 余次 margin 调整**，单轮提升全部 < 5%：

| 轮次 | 我在猜什么 | 结果 |
|---|---|---|
| 1 | 道具墙 margin-left 13 → 22 | +0.6% |
| 2 | comments margin 71 → 49 | −1.1%（改坏） |
| 3 | board margin −98 → −88 | −0.4%（改坏） |
| 4 | reward margin 202 → 48 | +17%（**唯一一次查出来的**） |
| 5~7 | reward 行高、规则区、第 6 行间距 | 各 +0.1~1.4% |

第 4 轮之所以能一次 +17%，是因为我先测了 `reward-bar` 的实际位置（1899）和目标（1900），算出差 151，而不是"看起来差很多"。

### 两类问题的分界线

```
结构问题  → 截图（视觉识别）   谁能和谁一行、几列、什么方向
数值问题  → 原产物 CSS         多少 px、什么色、什么字号、z 多少
```

原产物 `style_optimized.css` 里现成写着：

```css
.prop-bg-2-2 { position: absolute; left: 47px; top: 2497px; width: 148px; height: 88px; }
.btn-receive-2 { left: 37px; top: 34px; z-index: 68; width: 55px; height: 30px; }
```

这些是**事实**，不是估计。花 3 秒 `grep` 一下，比调 5 次 margin 快得多。

### 什么时候才允许估

只有原产物里**不存在**这个值的时候：

| 情况 | 处理 |
|---|---|
| 原产物有 `top: 2537px` | 查，直接用 |
| 原产物是流式（没有 top） | 按截图比例估，但估完要验证 |
| 想做原产物没有的间距（如统一 gap） | 估，但记下"这是我的选择"，不是"设计稿的值" |

### 与「禁止脚本」的关系

不冲突：

| 禁止 | 允许 |
|---|---|
| 脚本量 bbox 后聚类成行 | 人 `grep` 原 CSS 拿到 `top: 2537px` |
| 脚本按坐标差算间距 | 人读原 CSS 的 `margin-top: 5px` |
| 脚本生成 DOM 结构 | 人按截图写 `<div class="cell">` |

**前者是让脚本决定布局，后者是人从产物里取事实。**

### 反例：这次的三次返工都源于猜

1. `chest-row` 的 x 我写 43，实际该 40 → 猜的；
2. 评论区三层板 background-position 试了 0/68/118 三档 → 猜的（原 CSS 里有 `left/top`）；
3. 规则区 `margin-top` 试了 48/60/32 → 猜的（原 CSS 里 `top: 5482px` 摆着）。

三次都不需要猜——**打开 `style_optimized.css` 查对应 class 就有答案**。

## 21. 精度损失和效率浪费，各有三个固定来源

### 精度

| 来源 | 表现 | 实测 |
|---|---|---|
| 只查 `left/top`，漏 `padding/border/box-sizing` | 父容器取错，差 8px | 领取按钮判定反了（3.1） |
| 读 bbox 时 `Math.round` | 1px 以下被抹平 | 20 个元素累积 10~20px |
| 图片取渲染宽高当原图尺寸 | 有缩放时变形 | 宝箱列边缘发虚 |

**九件套**：`left / top / width / height / padding / margin / border / z-index / box-sizing`，一次查全。

**保留小数**：原产物里 `22.95px`、`19.55px`、`18.7px` 到处都是，`round` 一遍全丢。

### 效率

| 浪费 | 代价 | 改法 |
|---|---|---|
| 每次 `new_page` | 1.5s × 20 轮 = 30s 纯等待 | page 常驻 + `reload()`，0.3s |
| 每轮都整页算 | 20 轮里 15 轮位置根本没对上 | 先测 2~3 个目标元素（0.3s），对上再整页算 |
| 合成图重复生成 | 同样 20 张合了 3 遍（目录被删过 2 次） | `key = hash(names+bbox)` 命中直接复用 |

### 还有一处隐性浪费：图片缓存

同名覆盖更新后，浏览器仍用旧图。验收脚本每次新建 context 所以看到的是新的，**人看到的却是旧的**——这个差异让我以为"改了没生效"，多排查了两轮。

改法：覆盖更新时换文件名（`ui-btn-pending-2.png`），或加 `?v=hash`。

### 唯一能同时提速和提精度的

**目标值对照表**：动手前把原 CSS 的关键元素抄成 `元素 | left | top | w | h` 的表。

- 精度：之后所有测量是"对照"而不是"试探"；
- 效率：同一批 class 我 `grep` 了 15 次以上，有表就不用重复查。

77% 卡住的本质就是**没有这张表**——每次现查现猜。
