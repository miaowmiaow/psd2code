# psd2code 产物重排（截图定骨架 · 迭代收敛）

## 铁律

1. **第一步永远是整页截图 → 整页骨架。** 不分区块截图、不扫 DOM 定结构。
2. **骨架落成代码后先校验 `position` 占比**，不达标不进入资源填充。
3. **资源只搬产物里的原始文件**（图片文件、产物 DOM 里的文本节点），不截新图。

   **文字还是图片，由 DOM 的真实属性决定，不能凭视觉判断。**

   | 产物 DOM 里的实际形态 | 新结构怎么处理 |
   |---|---|
   | DOM 里是真实文本节点（`assets.json` 的 `txts` > 0） | 用文本，取原文 + 字号/颜色 |
   | 已转成图（`txts` 为 0，或该处只有一个 `background-image`） | **当作图片引用**，用那张图 |

   视觉上像文字、但 DOM 里是图片的，**绝不能手打文本**——字体、字距、加粗、橙色高亮全部对不上，而且它本来就有现成的图。实测该产物 `txts: 0`（全部文本已转图），我却把说明文字手打了一段，与原图差 20%。
4. **只有一种情况合成图片**：新结构某个位置只需要一张图，而产物那里是多层叠图，且这些图片的**重叠度 > 80%**。
5. **所有「布局相关」的工作禁止使用脚本，只能全视觉识别 + 手写。**
   布局相关包括：量坐标、按 y 聚类成行、按坐标差算间距/轨道、生成 HTML 结构、决定哪几个元素同行同列、把区块重建成 grid/flex。
   这类脚本一律不允许，出现即判定当次无效——**"用脚本算出网格参数再生成结构"，和"用脚本改原 DOM"，性质相同**。

   只有**非布局**的机械操作可以沉淀成脚本：

   | 允许 | 不允许 |
   |---|---|
   | 截整页/区域图 | 测 bbox 后聚类成行 |
   | 把重叠 > 80% 的多层图合成一张 | 算列轨道、行轨道 |
   | 像素对比、还原度计算 | 生成 DOM 结构 |
   | 提取资源清单（src / 原始宽高） | 决定间距、方向、对齐 |

6. **90% 是硬门槛，不是参考值。** 80% 属于"结构对、细节没对"，**不得视为可交付**，必须继续。
   每轮改完必须算**整页**还原度（忽略 1px 以内偏差），并同时报告：
   - 当前还原度、距 90% 还差多少个百分点；
   - 差异最大的 3 个 y 区间及各自差异率。

   判定走「总—分—总」：整页算 → 横带定位 → 修 → **再整页算**。区块对比只用于定位，不能用于宣布完成。
   单轮提升应 **> 5%**。**连续 3 轮 ≤ 5% 时，先验证骨架，再决定是否回退**——不能一看到提不动就回退：

   | 骨架验证项 | 判据 |
   |---|---|
   | `position` 占比 | < 10% |
   | 每个区块起点误差 | ≤ 2px（hero / 各 section 逐个测） |
   | 资源覆盖率 | 100%，或未用项已确认是装饰 |

   - **三项全过** → 骨架没问题，**不许回退**。提不动是因为精度手段不对，改用：逐元素对齐、补缺失资源、查原 CSS（铁律 7）、接受残差；同时上报。
   - **任一项不过** → 骨架错了，回第一步重走完整流程。

   实测教训：南瓜页三项全过（position 1.1%、区块 ≤2px、覆盖率 100%），仍按旧规则回退重走，结果必然还是同一个数值——**在正确的骨架上反复重走是最贵的浪费**。

7. **骨架靠视觉识别，属性靠读原产物样式算出来，不靠猜。**

   | 决策 | 依据 |
   |---|---|
   | 结构：谁和谁一行、几列、什么方向、嵌套几层 | **整页截图**（视觉识别） |
   | 数值：`left` / `top` / `width` / `height` / `margin` / `padding` / `font-size` / `color` / `z-index` | **原产物 CSS，直接查** |

   判定一个值该不该查：原产物里已经写着的（`top: 2537px`、`width: 146px`），**必须查**；
   只有原产物里不存在的（比如"这块该留多少白"），才允许按截图比例估。

   **猜数值是返工的唯一来源。** 实测本轮同一个页面调了 20 余次 margin，单轮提升全部 < 5%，
   每次都靠"看起来差 20px"试探；而查一次原 CSS 的 `top` 就能直接对位，误差 0~2px。

   这条与第 5 条不冲突：第 5 条禁止的是**用脚本量坐标/聚类成行**（那是让脚本定结构），
   这里要求的是**人去看产物 CSS 里写死的数值**（那是人取事实）。

## 为什么不能从 DOM 出发

产物的容器边界是设计师随手画的，不代表版面结构：

- `rounded` 一个容器里混着 13 个互不相关的东西；
- `group-col` 里塞了 7 个不同区块；
- 同名 class 结构各异（`prop-bg-2-2` ~ `prop-bg-2-18`）；
- 纯装饰拆成 3 层嵌套。

从这些边界出发写转换器，排出来的一定是「设计师的图层」，不是「页面的版面」。

## 四步法

### 第一步：整页截图 → 整页骨架

> **动手前先看 5.1（九件套一次查全）和 5.3（目标值对照表）。** 它们决定你后面是调 1 次还是调 20 次。

**输入**：一张整页截图（宽 = 设计稿宽，高 = 全页）。整页一起看，因为区块之间的关系（间距、对齐、层级）只在整页里成立。

**输出**：整页结构树，从上往下一行行写：

```
page
├ header          column，居中
│  ├ brand        column，间距 6
│  └ userbar      row，padding 18，间距 14
├ prop-wall       grid，4 列（142/142/142/139），列距 33/34/33
│  └ prop-card × 20   column，居中：icon / count / action
└ comment-list    column，间距 16
```

**这一步禁止使用脚本，后续所有步骤同样禁止用脚本做布局。** 骨架可以写在草稿里、边看边改，但"哪几个元素属于同一行、行与行之间隔多少、按什么方向排"必须是人判断的结果。

判断标准只有一条：**这段脚本是否影响"元素放在哪"**。影响 → 禁止；不影响（只影响像素怎么合、怎么比）→ 允许。

判定"我是不是在偷偷写脚本定布局"的三个信号：

- 用 `cluster(y)` / 距离容差把元素聚成行；
- 用 `margin = 本元素 y − 上一元素底` 算间距；
- 用循环把资源列表批量渲染成 HTML。

出现任意一条，本次产物作废。允许脚本做的事只有三件：把资源列成清单（src、原始宽高）、把多层图合成一张、跑像素对比。**只要脚本参与到"谁和谁同行、隔多远"，就已经越界。**

写法要求：

- 只写结构：容器类型、方向、列数、间距、对齐方式；
- **不写坐标**（`top: 792px` 属于旧世界）；
- 装饰单独标 `decor`，声明它脱离流；
- 同一类单元只写一次，标注数量。

判断依据全部来自截图：

| 截图上的样子 | 骨架判定 |
|---|---|
| 沿一个方向等距出现、交叉轴对齐 | `row` / `column` |
| 二维等宽重复 | `grid`，记列数与列宽 |
| 某个元素压在别的东西上 | `decor`，脱离流 |
| 大面积铺底 | 容器 `background`，不占子项 |
| 元素越出容器边界 | 确认是装饰出血，还是容器画小了 |

### 第二步：校验 position 占比

```
position: absolute 的规则数 / CSS 规则总数 < 10%
```

- 超了 → 骨架里还在用坐标摆东西，回第一步；
- 达标但视觉崩了 → 骨架的层级判断错了（容器边界认错、方向判反、间距归一化），同样回第一步。

**`position` 达标 ≠ 骨架正确**：实测有过 `position 0%` 但整页报废的结果（用通用转换器扫 DOM 得到）。

**「骨架通过」的完整定义（三项全过）**：

| 项 | 判据 | 怎么测 |
|---|---|---|
| `position` 占比 | < 10% | 数 CSS 规则里含 `position: absolute` 的条数 |
| 每个区块起点误差 | ≤ 2px | 逐个测 hero / 各 section 的 `[left, top]`，与原 CSS 对比 |
| 资源覆盖率 | 100%，或未用项已确认是装饰 | 见 4.2 |

三项全过 = 骨架可以保留，后面只在骨架上修精度；任一项不过 = 回第一步重写。

这条定义同时是铁律 6「连续 3 轮 ≤5%」时的判定依据：**三项全过就不许回退**。

### 第三步：资源填充

按骨架的槽位去产物里找资源：

| 槽位情况 | 处理 |
|---|---|
| 单层图片 | 直接引用原文件 |
| 多层叠图，重叠度 > 80% | 合成一张，按 **DOM 文档顺序**叠加（不是 z-index）；透明底；内容 hash 去重 |
| 多层叠图，重叠度 ≤ 80% | **不合成**，按骨架拆成多个槽位分别引用 |
| 文本（DOM 里是真实文本节点） | 取原文 + 字号/颜色，保持 DOM 文本 |
| 看着像文字、但 DOM 里是图（`txts` 为 0） | **按图片引用**，禁止手打文本 |
| 纯色/纯文字块 | 用 CSS 画，不硬凑图 |

**重叠度定义**：`交集面积 / 较小图面积`。> 80% 意味着小图基本完全落在另一张图里（如「南瓜主体 + 内部宝石」），视觉上是一个整体；≤ 80% 说明它们是并排或部分错开的独立元素，必须拆开。

三条硬规则（实测违反后分别导致 42% 还原度、300px 偏移、整屏重影）：

1. **背景、底板、按钮一律用原素材图，禁止手写颜色。**
   手写 `rgba(58,34,110,.86)` 代替 `rounded-407791.png` 会让整块板子的色差成为最大差异源。
2. **容器尺寸用素材的原始尺寸，不能靠内容撑开。**
   底板是 724×1698 / 704×1638 的固定图，靠内容撑开会让它缩成 800px，内部元素全部上移。
3. **同构单元用模板 + 数据**（共用 class + 内联变量），不复制 N 份结构。

**合成图片时必须带断言（同一个错误犯过两次：按钮变成纯蓝底、没有文字）：**

```python
# ① 文件不存在就停，不要 continue
missing = [n for n in names if not (images_dir / n).exists()]
if missing:
    raise SystemExit(f"素材缺失：{missing}")
# ② 图层没命中就停（防坐标范围写错）
if len({i['src'] for i in sel}) != len(names):
    raise SystemExit("图层未命中，检查 bbox 范围")
# ③ 合成后验证：文字类图放大看一眼，或统计非背景像素
```

`if not f.exists(): continue` 是这类 bug 的唯一来源——**静默跳过 = 错误被吞掉**。

像素对比抓不到它：空按钮和原版颜色几乎一致，整页差异只多 0.02%，只有"放大看"或"断言"能发现。

#### 3.1 判断槽位是「居中」还是「有意偏移」

写每个元素的 `margin` 之前，用**原版实测值**做基准（不是自己的估算值）：

```
居中值 = (父宽 − 子宽) / 2
偏差   = |原版实测 margin-left − 居中值|
```

| 偏差 | 判定 | 写法 |
|---|---|---|
| **< 3px** | 它本质是**居中** | 父容器 `align-items: center` / `justify-content: center`，不写 margin |
| **≥ 3px** | 是**有意偏移** | 写原版实测值，并注释"有意偏 N px" |

**基准必须是原版实测值，不能是自己的估算值。** 实测踩过这个坑：领取按钮父宽 146、子宽 55，居中值 45.5，我写了 45 并判定"居中"——但原版是 **37**，偏差 8.2px，是有意偏左。结果按钮整体右移 8px。

用"我的估算值 vs 居中值"比，等于自己跟自己比，永远能得出"是居中"。

**父容器必须取「视觉底图」，且换算到同一坐标系。**

原版常见三层结构：

```
.prop-bg-2-2   left 0    148×88    ← 中间容器（无背景），padding 0
.rounded-24    left -8   146×86    ← 视觉底图（有 background），这才是父容器
.btn-receive-2 left 37   55×30     ← 按钮，相对 .prop-bg-2-2
```

两种算法差 8px，结论完全相反：

| 用哪个当父容器 | 按钮相对位置 | 居中值 | 结论 |
|---|---:|---:|---|
| `.prop-bg-2-2`（148，未换算） | 37 | 46.5 | 偏左 9.5px ✗ |
| `.rounded-24`（146，换算 +8） | **45** | 45.5 | **居中（差 0.5px）** ✓ |

换算公式：

```
元素相对底图 = 原版绝对 x − 底图 x
```

按 148 的容器算，会得出"有意偏左 9.5px"的错误结论，然后把按钮往右挪——**改完更偏**。

判定前先问自己三件事：

1. 这个元素的**视觉底图**是哪一层（带 `background` 的那层）？
2. 原版元素的位置是相对谁算的？换算到"相对底图"要加减多少？
3. 换好坐标后，再和 `(底图宽 − 元素宽) / 2` 比。

**同构单元的多状态变体，尺寸和素材都要逐个查，不能套同一套参数。**

南瓜宝箱格有三种状态，按钮尺寸全不同：

| 状态 | 宝箱图 | 按钮尺寸 | 层数 |
|---|---|---|---:|
| 待开启 | `img-1002d0` 122×108 | `btn-locked` **77×31** | 3 |
| 已领取 | `img-ecff76` 117×113 | `btn-received` **69×22** | 10 |
| 领取 | `img-1002d0` 122×108 | `btn-receive` **55×30** | 3 |

我写了一套 margin 套三种状态 → 两个错（y 偏 15、x 偏 12）。

**但尺寸不同恰恰是「必须用 center」的证据**：任何固定 margin 只对一个变体成立，而三个变体在原版里**都是居中的**——一个 `align-items: center; justify-content: center` 同时覆盖全部。

改动后三个按钮与居中值完全一致（32/25、36/29、43/25），且以后新增状态不用重算。

> 同构单元的每个状态都要单独查 `src` 和尺寸。素材也可能不同（待开启用 `img-1002d0`、已领取用 `img-ecff76`），不能假定"都是宝箱所以同一张图"。

**实测（南瓜道具格，父宽 146）**：

| 元素 | 子宽 | 居中理论值 | 我写的 margin-left | 差值 | 正确写法 |
|---|---:|---:|---:|---:|---|
| 领取按钮 | 55 | 45.5 | 45 | 0.5 | `align-items: center` |
| 糖果+数量标签 | 68 | 39 | 41 | 2 | `align-items: center` |
| 南瓜图标 | 120 | 13 | 14 | 1 | `align-items: center` |

三个元素全部命中——**整个格子本来就是居中的，我却写成了三个魔法数字**。像素差只有 1~2px，看起来"对"了，但：

- 父容器宽度一变，元素就偏；
- 换一张不同尺寸的图，margin 又要重算（这次改尺寸重算了 5 次）；
- 读代码的人看不出为什么是 45。

**位置对 ≠ 结构对。** 渲染等价的两个写法，在可维护性上完全不同。

反向用法同样重要：差值 ≥ 3px 时不要强行居中——那是设计稿的真实偏移（如左侧图标留 14px 内边距），写成 center 反而错。

#### 3.2 重叠元素的层叠顺序：查原版 z-index，不要凭直觉

一个槽位里两个元素重叠时（糖果压着数量条、印章压着宝箱、文字压着底条），**谁在上面由原版的 z-index 决定**，不是由 DOM 顺序、也不是由"通常谁该在上面"。

```
z 大的在上
z 相同 / 都没设 → 按 DOM 顺序，后出现的在上
```

实测（南瓜道具格）：

| 元素 | z-index | 视觉 |
|---|---|---|
| `candy-299b89`（糖果图标） | **71** | 压在数量条上 |
| `rect-166527`（数量条） | **69** | 在糖果下 |

我按 DOM 顺序写成「糖果 → 数量条」，数量条后绘制 → 盖住了糖果。正确写法是**糖果放在 DOM 后面**（或给数量条让位），让它后绘制。

写代码时的检查顺序：

1. 这一组里有重叠吗（bbox 相交面积 > 0）；
2. 有 → 查原版两元素的 `z-index`；
3. z 不同 → z 大的放 DOM 后面（或显式 `z-index`）；
4. z 相同 → 原版 DOM 里谁在后面，谁就在上面。

**合成多图层时，排序依据是 `z-index`，不是 bbox 的 `y`。**

实测（任务卡标题）：`rect-7ff85d`（底条，y=2444，**z=333**）和 `task-f4ad77`（文字，y=2428，**z=334**）。

- 按 y 排序 → 底条 y 更大，后绘制 → **盖住文字**（「每日任务」只剩上半截）
- 按 z 排序 → 文字 z 更大，后绘制 → 正确

我第一版就是按 `(y, x)` 排的，结果三张任务卡的标题全被底条压住。

**判定**：合成前先按 z 升序排一遍；z 相同才退回 DOM 顺序。

**不要用"文字总该在上面"这类直觉**——实测原版有 `rect`（z=285）压在静态文字之上的情况，那是设计稿的真实层叠。

#### 3.3 z 值差 > 100 说明是「浮层」，不是格内元素

一个区块里所有元素都有 z 值，但**它们不一定属于同一套层叠体系**。看南瓜「已领取」宝箱格的 z 分布：

```
z = 306  宝箱         ┐
z = 307/310 圆底      │
z = 308/311 印章      ├─ 内容层（306~316）
z = 314  按钮文字     │
z = 316  灰条         ┘

z = 525  「去拿糖果」竖条  ┐
z = 526  竖排文字         ├─ 浮层（525~527）
z = 527  鬼魂             ┘
```

差 219。**竖条和鬼魂不是格内元素，是全局浮层。**

判定：同一个 bbox 内，`z_max − z_min > 100` → 存在两套体系。

| 类型 | 处理方式 |
|---|---|
| 内容层（z 相近，如 306~316） | 作为格的 flex 子项正常排布 |
| 浮层（z 高出 100+） | **脱离流**：单独放，用负 margin 或定位，绝不塞进格的 flex 里 |

把浮层塞进 flex 的后果：它会被父容器拉伸/裁切，或把格子的高度撑开，而它在原设计里是**盖在整个页面之上**的。

这条和"装饰标 `decor`"是同一件事的两个视角：`decor` 说的是**语义**（它不属于这个槽位），z 差说的是**怎么认出来**。

#### 3.4 独立定位（grid 叠同格）的适用边界

**独立定位**指：让子元素各自相对**容器**定位，而不是相对兄弟元素。

```css
.container { display: grid; }
.container > * { grid-area: 1 / 1; align-self: start; justify-self: start; }

.a { margin: 34px 0 0 184px; }   /* 相对容器左上角，与兄弟无关 */
.b { margin: 103px 0 0 528px; }
```

对比「负 margin 串联」（`.b { margin: -51px 0 0 498px }`）——后者绑定了前一个元素的具体尺寸，一旦前一个变了，整组飞。

**但有硬约束：容器高度不再由子元素累加决定。**

| 容器高度的来源 | 能否用 grid 叠同格 |
|---|---|
| **max(子元素高度)** —— 单图格、图标组、宝箱槽 | ✅ 安全 |
| **累加** —— 标题高 + margin + 正文高 + 页脚高 | ⚠️ **必须显式给容器高度**，否则塌陷 |

实测（南瓜页 6 处负 margin 改造）：

| 位置 | 容器高度来源 | 结果 |
|---|---|---|
| 宝箱槽 `.chest-slot`（宝箱 + 黄条） | max(108, 82+80) | ✅ 成功 |
| 第 6 行 `.chest-row`（4 个槽） | max(图高) | ✅ 成功（另改为固定宽度） |
| 奖励条 `.reward-bar`（提示 + 图标行） | max | ✅ 成功 |
| 任务卡 `.task-card`（标题 + 链接 + 正文） | **累加** | ❌ 页面少 47px，79.77% → **70.92%** |
| 任务行 `.task-row`（主行 + 奖励） | **累加** | ❌ 同上 |
| 评论 `.comments`（标题 + 板） | **累加** | ❌ 同上 |

回退后者的原因：`body` 的 `margin-top: 22` 原本**会把 flex 容器撑高**，改 grid 后三个子元素占同一格，`margin` 只影响绘制位置、不参与高度计算 → 整页少 47px → 后面全部上移。

**判定顺序**：

```
这个容器的高度是"最高的那个子元素"还是"几个子元素加起来"？
  后者 → 改 grid 时必须同时写 height
  前者 → 直接改，安全
```

### 第四步：两遍走 —— 先整体，后细节

**不要一遍把结构和像素一起做。** 实测这样做的成本是两遍法的 3 倍以上：每加一个元素都要同时决定"放哪 + 隔多少 + 后面全部重算"，改一次 margin 全页重算。

#### 4.0 第一遍：只看整页截图，把结构立住

目标只有一个：**flex 布局率达标 + 位置大致对**。

- 用**一张整页截图**定所有区块、行、列、方向；
- 每块只保证"起点大致对、内部是 flex"；
- `position` 占比压到 10% 以下；
- **不追细节**，间距靠整页比例估，允许差 20~30px；
- 这一遍完成后，还原度大概在 60~70%，是对的。

把 `position` 降下来必须在这一遍完成——它是结构属性，后面补细节时改不动。

#### 4.1 之后各遍：区域**定位** → 整页**判定**

**区域截图只回答"哪里不对"，不回答"对不对"。** 判定永远看整页（见 4.3）。

- 用区域截图找出问题在哪一块、哪一类（间距 / 缺失资源 / 层叠），不要每次全页重算定位；
- 每轮只修一个区块、一类问题；
- **必须查原产物的 CSS 数值**（`top` / `left` / `width` / `margin` / `font-size`）——它是精度的来源，不是结构的来源。
  结构仍以截图为准，但"这一行该在 2497px"这种数值**直接查原 CSS，不许试错**（见铁律 7）。

**80% → 90% 这一段必须逐元素对齐，不能整块调。**

78~85% 之后，剩下的差异基本不是"整块错位"，而是单个元素差 5~30px。这时整块调 margin 的收益接近 0（甚至为负），必须：

1. 用 Playwright 一次性打印该区块**每个元素**的 `[left, top, width, height]`；
2. 与原产物的 CSS 值逐个比对，列出偏差表；
3. **一次改一个偏差**（改完立刻重测该元素，不看整页）；
4. 全部元素误差 ≤ 2px 后，再算整页还原度。

实测：南瓜页在 81.7% 卡住时，把「橙色板 `img-0856c7` 的 y 从 2046 改到 2304」一处修正就 +7.29%——**那一处就是"整块调不动、单点一改就通"的典型**。

```css
/* 原产物 style_optimized.css 里现成的精确值，直接用作 margin 参考 */
.prob-bg-2-2 { left: 47px; top: 2497px; }
```

**允许查原 CSS 的边界**：只用于"对齐数值"（位置、尺寸、颜色、字号），不用于"决定结构"（谁是谁的子元素、该怎么分组、方向是什么）。

#### 4.2 先核对资源覆盖率（最容易漏的一步）

把产物 `assets.json` 里的全部资源列成清单，逐个标记"是否已在新结构中用到"：

```
图片 366 个 / 文本 0 个        ← 文本数取自 assets.json 的 txts，不是肉眼判断
已用 344 / 未用 22
未用清单：
  img-031  images/chest-0545ad.png   [578,44,138,69]
```

**文本数是 0 时，说明该产物所有文字都已转图**，覆盖率清单里就不会出现 `txt-*` 项——所有"文字"都应该在图片清单里找到对应文件。

**未用资源 = 细节缺失**，说明骨架漏了槽位或某个元素被吞掉。此时不要继续调间距，**回到第一步重新校验该区域的骨架**，确认这个资源属于哪个区块、哪个槽位。

只有「覆盖率 100% 或剩余项已确认是装饰/冗余」时，才进入像素迭代。

**三项工作的分工（避免"366 个资源怎么人工核"的困惑）**：

| 步骤 | 谁做 | 是否允许脚本 |
|---|---|---|
| 导出资源清单（src + bbox） | 脚本 | ✅ 非布局 |
| 扫新结构实际用到哪些 src | 脚本 | ✅ 非布局 |
| 差集里哪些是"漏掉的结构元素"、哪些是"装饰/冗余" | **人判断** | ❌ 这是结构决策 |

脚本只负责把差集摆出来，**归类和补不补由人定**。

#### 4.3 像素迭代：总—分—总

**判定只认整页。** 区块对比只用来定位，不能用来宣布完成。

**① 总：整页算一次**

```bash
# 必须整页：宽 = 设计稿宽，高 = 全页高度
还原度 = 1 - (maxΔ > 1 的像素数 / 总像素数)
```

忽略 1px 以内偏差：通道差 ≤ 1 视为一致（8bit 量化与抗锯齿的正常范围）。不要用阈值 8（会漏掉整片抗锯齿区），也不要用 0（会把合成舍入差算成错误）。

**② 分：定位差异**

- 按 200px 横带统计差异率，找出差异最大的 2~3 段；
- 必要时截该区块做左右/上下对比；
- 区分形态：整体重影（累积偏移）／均匀色差（背景错）／局部纯色块（元素缺失）。

**③ 总：修完再整页算一次**

每轮修完必须回到第 ① 步。**不允许「分块都过了就宣布完成」**——分块算发现不了块与块之间的错位。

**循环判定**

> **「一轮」= 一次整页还原度计算。** 不是"改一处"，也不是"改一个区块"——一轮里可以改多处，只要最后跑一次整页算、得到一个数值。

| 条件 | 动作 |
|---|---|
| 整页还原度 ≥ 90% | 完成 |
| < 90%，本轮提升 > 5% | 继续下一轮（回 ①），**清零连续计数** |
| < 90%，本轮提升 ≤ 5% | 继续（回 ①），**连续计数 +1** |
| < 90%，**连续 3 轮提升 ≤ 5%** | **回到第一步，重走完整流程** |

最后一档是关键：连续 3 轮提不动，说明**骨架本身有问题**（容器边界认错、方向判反、层级切错），继续调间距/尺寸不会有质变。此时必须**重新整页截图 → 重写骨架 → 重新校验 position → 重新填充**，而不是在错的骨架上修补。

上报时必须同时给出：当前整页还原度、距 90% 的差、差异最大的 3 个横带、以及「我判断骨架哪一层可能错了」。

#### 4.4 80% 之后的差异来源（为什么整块调没用）

| 现象 | 真实原因 | 修法 |
|---|---|---|
| 整块差异 30~60%，但结构看着对 | 某张大图/底板的位置错了 100~300px | 查该图的实测 bbox，直接对齐 |
| 一段区间差异 40%+ 且边缘有重影 | 整块被前后内容顶偏 | 对齐该块起点，不改内部 |
| 差异均匀散布、每处 5~20px | 元素级 margin 估算误差 | **逐个元素**比对 bbox |
| 局部小片 90%+ | 内容缺失（漏了元素/整行） | 对照资源覆盖率清单补 |

**80% 是分水岭**：在此之前改"块"有效，在此之后只有改"点"有效。

#### 4.5 差异形态与修法

| 形态 | 含义 | 修法 |
|---|---|---|
| 每个元素都有偏移轮廓（重影） | 累积偏移 | 容器定尺寸、关键节点定高 |
| 整片均匀色差 | 背景不对 | 换回原素材，别手写颜色 |
| 局部纯色块 | 元素缺失/多余 | 对照覆盖率清单，补/删该槽位 |

## 五、精度与效率手册

上面的四步法不变。这一节是**工具级手法**，专门解决"能对但太慢"和"改对又改坏"两类问题。

### 5.1 取值：九件套一次查全

查一个元素的原产物数值时，一次把九个属性全抄下来，不要单项查：

```
left / top / width / height / padding / margin / border / z-index / box-sizing
```

实测只查 `left` 会漏掉关键信息：

```css
.prop-bg-2-2 { left: 0;   top: 114px; width: 148px; height: 88px; padding: 0; }
.rounded-24  { left: -8px; top: -8px;  width: 146px; height: 86px; }
.btn-receive-2 { left: 37px; top: 34px; width: 55px; height: 30px; }
```

「按钮的父容器是 148 还是 146」这个 8px 的疑问，答案就藏在 `padding: 0` 和 `left: -8px` 里。**只查 left/top 会反复掉进坐标系陷阱（见 3.1）。**

### 5.2 保留小数，禁止 `round()`

原产物里大量非整数：

```css
.username  { font-size: 22.95px; }
.server    { font-size: 19.55px; }
.ops       { font-size: 18.7px; }
```

读 bbox 时如果用 `Math.round`，1px 以下全被抹平；20 个元素累积就是 10~20px 的整体偏移。

**读和写都保留一位小数**：

```python
[round(v, 1) for v in bbox]      # 不是 round(v)
```

### 5.3 对齐：先建「目标值对照表」

动手写代码之前，把原产物 CSS 里所有关键元素抄成一张表：

| 元素 | 原 class | left | top | w | h | 备注 |
|---|---|---:|---:|---:|---:|---|
| 道具墙 | `.rounded-2` | 39 | 678 | 704 | 1638 | 板 |
| 第一格 | `.section-bg-3 > div:first` | 47 | 678 | 142 | 196 | 格 |
| 领取按钮 | `.btn-receive-2` | 47 | 148 | 55 | 30 | 相对格 |

之后所有测量都是**对照**，不是**试探**。这张表是唯一能同时提升精度和速度的东西。

实测：同一批 class 我 `grep` 了 15 次以上，每次都在重新确认同一个值。

### 5.4 定位：用「差异连通域」，不要只看横带

200px 横带只能告诉你"这 200px 差 30%"。改成连通域分析，直接指到元素：

```
差异块 #1  bbox(47, 2534, 138, 78)    面积 30%   ← 某个按钮
差异块 #2  bbox(568, 1690, 187, 214)  面积 62%   ← 金色宝箱
```

比"切图 → 看图 → 猜"快一个数量级。实现是纯像素处理，不涉及布局决策（允许）。

**边界**：连通域只输出 `bbox` 用于"哪里差"，**不产生任何图片资源**（不违反铁律 3 的"不截新图"），也不决定结构（不违反铁律 5）。

### 5.5 图片：查 `naturalWidth`，不是渲染宽高

```js
img.naturalWidth                        // 142  原图像素
img.getBoundingClientRect().width       // 146  渲染尺寸
```

两者不一致说明原产物有缩放。新结构必须写 `width:146px` 并引用**原图**，不能换图或让浏览器自己缩——否则变形，边缘模糊。

### 5.6 分组：用 z-index 推断「谁和谁是一组」

原产物每个元素都有 z，**z 相近（±3 内）且 bbox 相交的元素通常是同一组**：

```
z=67 rounded-24 (146×86)      黄条底
z=68 btn-receive-2 (55×30)    按钮
z=71 candy-299b89 (28×28)     糖果
z=72 group-2 (68×30)          徽章组
z=73 prop-bg-2-2 (148×88)     容器
```

67~73 连续且互交 → 明显是同一个「卡片体」。

这是**人读数据判断结构**，不是脚本聚类。区别在于：脚本会自己决定分组，而这里是人看 z 值确认自己的判断。

### 5.7 迭代：先测点，再整页

规则要求每轮整页算（对），但中间步骤可以快：

```
改 → 测这 2~3 个目标元素的位置（0.3s）→ 对上了 → 整页算还原度（2s）
```

实测 20 轮里有 15 轮是白算——位置根本没对上就整页算了。

**判定顺序**：目标元素 bbox 对齐 → 再看该区块差异 → 最后整页。

### 5.8 效率：三个缓存

| 缓存 | 做法 | 省的 |
|---|---|---|
| Playwright page | 复用同一个 page，改完 CSS 后 `reload()` | 每次省 1.2s（160 张图的重新加载） |
| 合成图 | `key = hash(names + bbox)` 命中直接返回文件名 | 同样 20 张图合了 3 遍 |
| 图片版本号 | 覆盖更新时改文件名（`ui-btn-pending-2.png`）或加 `?v=hash` | 省掉"以为没修好"的排查循环 |

图片版本号那条尤其重要：同名覆盖后浏览器仍用旧图，**验收截图（新 context，不吃缓存）和你看到的画面会不一致**，实测被骗过两次。

## 反模式

| 反模式 | 为什么错 |
|---|---|
| 写 `flexify.py` 这类通用转换器 | 版面结构没有共性；跑出来 position 0%、页面报废 |
| 从 DOM 容器边界推骨架 | 继承的是设计师的图层分组，不是版面 |
| 用坐标统计猜方向/间距 | x/y 谁 spread 大不代表语义；间距归一会逐级累积误差 |
| 手写 `rgba` 当背景 | 素材图自带渐变/描边/阴影，手写色必然有色差 |
| 容器靠内容撑开 | 底板是固定尺寸，撑开就错位 |
| 分区块截图定结构 | 丢掉区块之间的间距与对齐关系 |
| 追求 `position` 指标而牺牲视觉 | 指标完美 ≠ 结构合理 |
| 把整格/整块截成图片 | 背景被固化、素材不可复用、有状态的控件被烧死（**任何层数都不例外**） |
| 跳过资源覆盖率直接调像素 | 漏掉的元素调间距调不回来 |
| 为了 diff 好看退回绝对定位 | 等于没做重排 |

**整格合成一律禁止**（实测代价）：

| 做法 | 后果 |
|---|---|
| 10 层合成一张 `ui-done-box.png` | 换肤失效、状态不可切、单个印章/文字无法微调、文字颜色改不了 |
| 逐层还原（grid 叠同格） | 位置同样能精确到 1px，且每层可独立替换 |

曾被"层数 > 6 或含浮层"这条例外放行过一次，结果那格成了黑盒——**层数多不是合成的理由，恰恰是必须逐层的理由**。

浮层（z 差 > 100，见 3.3）也不用合成：它们本来就该脱离流单独放。
